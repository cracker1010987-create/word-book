# add-feature

wordbook 프로젝트에서 기능을 하나 추가할 때 항상 이 순서를 따른다.
**한 번에 조각 하나만** 다룬다. 여러 조각을 동시에 만들지 않는다.

먼저 `CLAUDE.md`와 `prd.md`를 읽어서 이 프로젝트의 규칙과 기술 결정을 파악한다.
특히 `prd.md`의 기술 결정(③) — JSON 파일 하나로 저장, LLM 호출은 `ai.py`에만 두고 체인은
인자로 주입, `today`는 항상 파라미터로 받음 — 을 어기는 코드를 쓰지 않는다.

## ① 조각 확인

`TASKS.md`를 읽고 이번에 만들 조각을 찾는다. 사용자가 조각 이름을 지목했으면 그것을,
아니면 아직 체크되지 않은 것 중 순서가 가장 빠르고 선행 조각이 이미 끝난 것을 고른다.

그 조각의 검사 방법이 **pytest**인지 **AI 심판**인지 확인하고, 아래 ②/③ 중 맞는 절차로 간다.

## ② pytest 조각인 경우

1. 구현 코드를 쓰기 **전에** `tests/`에 테스트를 먼저 작성한다.
2. pytest를 실행해서 실패(Red)하는지 확인한다. (아직 구현이 없으니 실패하는 게 정상이다.)
3. **[GATE]** 테스트 내용을 사용자에게 보여주고 "이 테스트가 맞나요?"라고 확인받는다.
   확인 전에는 구현으로 넘어가지 않는다.
4. 확인받으면 구현 코드를 짠다. **테스트 파일은 절대 고치지 않는다** — 통과가 안 되면
   구현을 고친다.
5. pytest가 전부 통과할 때까지 구현을 반복하고, 마지막 통과 화면을 보여준다.

## ③ AI 심판 조각인 경우

1. `rubric/`에 이 결과물을 평가할 채점표가 있는지 확인한다.
   - 없으면 먼저 채점표를 만들고 **[GATE]** 사용자에게 확인받는다.
2. 결과물을 실제로 생성한다 (예: `make_quiz`처럼 실제 API를 한 번 호출).
3. 그 채점표를 기준으로 채점하는 심판 에이전트(예: `quiz-judge`)를 Agent 도구로 호출해서
   평가한다. 해당하는 심판 에이전트가 없으면 `rubric/`의 채점표를 그대로 따르는
   general-purpose 에이전트로 대신한다.
4. verdict가 FAIL이면: 무엇이 왜 부족한지 확인하고, 프롬프트나 구현을 고쳐서 다시
   생성 → 다시 채점한다. **verdict가 PASS 될 때까지 반복한다.**
   같은 원인으로 반복 실패하면(예: 3번 이상), 무작정 더 시도하지 말고 사용자에게
   상황을 보고하고 다음 방향을 물어본다.

## ④ 완료 처리

- `TASKS.md`에서 이번 조각에 체크 표시를 한다.
- 무엇을 만들었는지 **3줄로** 보고한다 (무슨 조각을, 어떤 방식으로 검증했는지, 결과).

## 지켜야 할 것

- `prd.md`의 기술 결정을 어기지 않는다.
- 한 번에 조각 하나만 만든다. 다음 조각은 이번 조각이 끝나고 사용자가 원할 때 시작한다.
- `.py` 파일을 쓰거나 고치면 `PostToolUse` 훅(`check.py`)이 자동 실행된다. 실패하면
  설명만 하지 말고 CLAUDE.md의 "훅 위반 대응" 규칙대로 그 자리에서 바로 고친다.
